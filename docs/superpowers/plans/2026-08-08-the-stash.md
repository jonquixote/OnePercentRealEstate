# The Stash — Cold Inventory That Keeps Its Value

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move cold listings aside so they stop costing us on every scan, while keeping every row queryable and keeping the history that makes an old listing worth having.

**Architecture:** Not deletion, not even really archival — a *stash*. A listing that goes quiet moves to cold storage with its history intact; when the crawler sees it again it comes straight back. The decision "in or stashed" is made by one rule, recorded, and reversible. Compression is applied where it actually pays, which the measurements say is TOAST rather than the heap.

**Tech Stack:** PostgreSQL 16 (LZ4/pglz TOAST compression), `services/scraper_service`, `apps/one`, bash ops scripts.

## Why a stash rather than a purge

Old listings are not junk. A property that sold eighteen months ago is a comp. A
listing that cycled on and off the market three times is a motivated seller. The
price history of a listing that sat for 200 days *is* the deal signal — the
product already computes `price_cut_pct` and `days_on_market` from exactly this
kind of history.

So the requirement is not "get rid of cold rows", it is: **cold rows must stop
costing us on every scan while staying available and keeping their history.**

## The measured problem

Prod, 2026-07-26:

| Lifecycle | Rows | Share |
|---|---|---|
| `stale` | **772,904** | **58.5%** |
| `active` | 446,270 | 33.8% |
| `sold` | 77,198 | 5.8% |
| `pending_verify` | 41,237 | 3.1% |
| `rental_misfiled` | 2,877 | 0.2% |

Where the 11 GB actually lives:

| | size |
|---|---|
| heap | 4,418 MB |
| **TOAST** | **5,473 MB** |
| indexes | 1,428 MB |

**TOAST is larger than the heap.** The bulky columns are `raw_data`, `images`,
`description`, `nearby_schools`, `agent_info`, `tax_history`.

And compression is inconsistent:

```
raw_data        attcompression = l   (LZ4)
images          attcompression = ''  (default -> pglz)
description     attcompression = ''  (default -> pglz)
nearby_schools  attcompression = ''  (default -> pglz)
agent_info      attcompression = ''  (default -> pglz)
tax_history     attcompression = ''  (default -> pglz)
default_toast_compression = pglz
```

Only `raw_data` was ever switched to LZ4. Everything else still uses pglz, which
is both slower to decompress and generally weaker on this kind of JSON — and
`images` in particular is read on **every listing card**, where the TOAST fetch
was measured at 1.939 ms versus 0.119 ms for a native column.

## What already exists

`2026-08-03-cold-listings-archival.md` shipped the foundations, with **zero rows
moved**:

- `listings_archive` exists on prod, empty, with only the two indexes its access
  patterns need.
- The property loader reads through: live table first, archive on a miss.
  Verified in production against the empty archive — `/property/877` 200 in
  45 ms, `property.id` p95 unchanged.
- The crawler resurrects an archived listing before its upsert, so a returning
  listing cannot become a duplicate.

**One scar from that work must not be repeated.** The resurrection query used
`INSERT INTO listings SELECT *`, but `listings.rent_price_ratio` is
`GENERATED ALWAYS` while `listings_archive` (created with
`LIKE ... INCLUDING DEFAULTS`, which does **not** copy generated-ness) holds it
as a plain column. Every scrape insert failed with a 500 and **the crawl produced
nothing for 80 minutes**. Columns must be enumerated with
`is_generated = 'NEVER'`; never `SELECT *` between these two tables.

## Global Constraints

- **Nothing is deleted, ever.** Rows move between `listings` and `listings_archive` and back.
- **Every stashed listing stays reachable.** `/property/[id]` must render it — old links, shared URLs, ~34k sitemap entries.
- **History travels with the row.** `listing_price_history` (and any other child table) must remain joinable for a stashed listing, or the stash destroys the thing that made the row worth keeping.
- **Never `SELECT *` between the two tables** — see the scar above.
- **The "in or stashed" decision is one rule, in one place.** Two implementations will disagree, and the disagreement will be invisible.
- **Rehearse on a restored snapshot before prod.** UpCloud Simple Backup (`0430,dailies`).
- **Bounded, paced, resumable batches**, watching `db-load-budget.sh` and `crawl-health.sh`.
- **Measure compression before and after `VACUUM FULL`/rewrite** — the space is not returned until the table is rewritten, and numbers taken before that are not real.

## Task 1: Compression where it actually pays

**Files:**
- Create: `infrastructure/migrations/2026_08_08_lz4_toast_columns.sql`
- Create: `docs/perf/2026-08-compression-audit.md`

**Interfaces:**
- Produces: measured compression ratios per column, and LZ4 on the columns where it wins.

- [ ] **Step 1: Measure what each column actually costs**, before changing anything:

```sql
SELECT
  pg_size_pretty(sum(pg_column_size(raw_data))) AS raw_data,
  pg_size_pretty(sum(pg_column_size(images))) AS images,
  pg_size_pretty(sum(pg_column_size(description))) AS description,
  pg_size_pretty(sum(pg_column_size(nearby_schools))) AS nearby_schools,
  pg_size_pretty(sum(pg_column_size(agent_info))) AS agent_info,
  pg_size_pretty(sum(pg_column_size(tax_history))) AS tax_history
FROM listings TABLESAMPLE SYSTEM (2);
```

Scale the sample up. **This decides whether Task 1 is worth doing at all** — if
one column dominates, only that column matters.

- [ ] **Step 2: Compare LZ4 against pglz on real data**, not on reputation:

```sql
SELECT pg_size_pretty(sum(pg_column_size(images::text::jsonb))) AS as_is,
       pg_size_pretty(sum(octet_length(images::text))) AS uncompressed
  FROM listings TABLESAMPLE SYSTEM (1) WHERE images IS NOT NULL;
```

Record the ratio per column. LZ4 usually trades a little ratio for much faster
decompression — and `images` is read on **every card**, so decompression speed
matters more than ratio there.

- [ ] **Step 3: Switch the columns where the measurement supports it.**

```sql
ALTER TABLE listings ALTER COLUMN images SET COMPRESSION lz4;
ALTER TABLE listings ALTER COLUMN description SET COMPRESSION lz4;
-- …and the rest, per Step 2
```

**`SET COMPRESSION` affects only newly written values.** Existing rows keep
their current compression until rewritten. Say so in the audit so nobody expects
an immediate size drop.

- [ ] **Step 4: Set the database default** so new columns inherit the decision:
`ALTER DATABASE postgres SET default_toast_compression = lz4;`

- [ ] **Step 5: Measure the read-path effect** — the `images` TOAST fetch was
1.939 ms / 94 buffers before. Re-run that measurement on rows written after the
change and record it.

- [ ] **Step 6: Commit** — `perf(db): LZ4 on the TOASTed columns that earn it`

## Task 2: One rule for "in or stashed"

**Files:**
- Create: `apps/worker/src/stash-rule.ts`, `apps/worker/src/stash-rule.test.ts`
- Create: `infrastructure/migrations/2026_08_08_stash_metadata.sql`

**Interfaces:**
- Produces: `shouldStash(listing): { stash: boolean; reason: string }`

- [ ] **Step 1: Write the failing tests.** This rule decides what the product can
see, so it is specified before it is written:

```ts
describe('shouldStash', () => {
  it('never stashes an active listing, however old', () => {
    expect(shouldStash({ status: 'active', lastSeenDaysAgo: 400 }).stash).toBe(false);
  });

  it('stashes a stale listing unseen beyond the threshold', () => {
    expect(shouldStash({ status: 'stale', lastSeenDaysAgo: 200 }).stash).toBe(true);
  });

  it('does NOT stash a recently stale listing — it may come straight back', () => {
    expect(shouldStash({ status: 'stale', lastSeenDaysAgo: 10 }).stash).toBe(false);
  });

  it('keeps sold listings hot enough to serve as comps', () => {
    // Sold listings are the comp set. Stashing them cheaply is how a rent model
    // loses its evidence.
    expect(shouldStash({ status: 'sold', lastSeenDaysAgo: 200 }).stash).toBe(false);
  });

  it('always gives a reason, so a stashed row can be explained later', () => {
    expect(shouldStash({ status: 'stale', lastSeenDaysAgo: 200 }).reason).toMatch(/\w/);
  });

  it('treats a missing last-seen as NOT stashable — never stash on ignorance', () => {
    expect(shouldStash({ status: 'stale', lastSeenDaysAgo: null }).stash).toBe(false);
  });
});
```

- [ ] **Step 2: Run them, watch them fail, then implement.** One pure function,
no database access, so the rule can be unit-tested and reused by both the
stashing job and the resurrection path.

- [ ] **Step 3: Record the decision on the row.** Add `stashed_at timestamptz`
and `stash_reason text` to `listings_archive`, so every stashed row can answer
"why am I here?" — the same principle as `rent_calc_error`.

- [ ] **Step 4: Commit** — `feat(stash): one rule for in-or-stashed, with a recorded reason`

## Task 3: History must travel with the row

**Files:**
- Create: `infrastructure/migrations/2026_08_08_history_follows_stash.sql`
- Test: alongside the stash job

**Interfaces:**
- Consumes: the stash rule from Task 2.

- [ ] **Step 1: Find every table that references a listing.**

```sql
SELECT tc.table_name, kcu.column_name
  FROM information_schema.table_constraints tc
  JOIN information_schema.key_column_usage kcu USING (constraint_name)
  JOIN information_schema.constraint_column_usage ccu USING (constraint_name)
 WHERE tc.constraint_type = 'FOREIGN KEY' AND ccu.table_name = 'listings';
```

Also grep for `listing_id` on tables without a declared foreign key —
`listing_price_history`, `rent_predictions_audit`, saved properties, alerts.
**A child row orphaned by a stash is history destroyed**, which defeats the point.

- [ ] **Step 2: Decide per child table, and record the decision**, because they
differ:
  - **`listing_price_history`** — the deal signal. Must remain joinable.
  - **`rent_predictions_audit`** — already partitioned; likely stays put.
  - **saved properties / alerts** — reference listings a *user* cares about.
    **A stashed listing that a user saved must still resolve**, or the stash
    silently breaks their shelf.

- [ ] **Step 3: Write the failing test** proving a stashed listing's price
history is still retrievable through the read-through path.

- [ ] **Step 4: Implement**, then verify on the rehearsal database that a stashed
listing renders with its full price history and days-on-market intact.

- [ ] **Step 5: Commit** — `feat(stash): history follows the listing into the stash`

## Self-Review

**Spec coverage:** the requirement — cold rows stop costing us on every scan
while staying available and keeping their history — is met by compression where
it pays (T1), a single recorded in-or-stashed rule (T2), history that follows the
row (T3), and a rehearsed, reversible move (T4). The archival foundations already
shipped are reused rather than rebuilt.

**Placeholder scan:** every step names files, exact SQL, and what to verify. The
one open value — the staleness threshold for stashing — is specified by test in
T2 rather than asserted here, and deliberately errs toward *not* stashing
(missing last-seen never stashes).

**Type consistency:** `shouldStash(listing): { stash: boolean; reason: string }`
is the only new runtime contract, shared by the stash job and the resurrection
path so the two cannot disagree about what belongs where.
